## 1. 背景、范围和非目标

当前实现位于 `cmd/opskit/main.go`、`internal/app/{app,config,check}.go`，已有命令：

| 命令 | 当前已实现的能力 | 明确限制 |
|---|---|---|
| `version`、`config init` | 版本展示、生成配置模板且不覆盖现有文件 | 暂无 `config validate` 或 `config show` |
| `etcd check` | 通过 `etcdctl` 查询成员、状态和健康；输出 JSON | 顺序探测的 quorum 仅是观察值，不代表持续可用；未执行 hashkv |
| `etcd backup` | `etcdctl snapshot save`；独立目录、SHA-256、manifest、可选上传 | 尚无自动恢复验证与本地保留策略 |
| `s3 check` | HeadBucket、可选 HeadObject；JSON 诊断 | 只读 HEAD 不证明写入权限 |
| `s3 upload` | AWS SDK v2 上传，条件写及 HEAD 元数据核验 | 未实现下载回读校验、列举或下载命令 |

当前配置为 `schema_version: 1` 的 `timeout`、`etcd`、`s3`，包括 `minio/aws/custom` 厂家块和旧式平铺 S3 字段。现有清单字段仅为 `schema_version`、`file`、`size`、`sha256`、`created_at`、`upload_status`、`remote_key`；没有单独的 task_id 或备份 phase 字段。

**本轮非目标**：修改业务代码、增加网络诊断、引入常驻服务、实现 MySQL/PostgreSQL、增加生产自动恢复、自动删除备份、立刻改动已有配置 Schema 或现有 JSON 输出。`go-opskit-design.md` 中的网络、数据库和容器规划属于后续愿景，不应写成已经交付。

## 3. 渐进式架构

```text
cmd/opskit/main.go
  └─ CLI 解析、帮助与退出码（保留用户接口）
       ├─ config：解析、验证、路径/凭据来源
       ├─ etcd：etcdctl 命令构造、成员探测、快照
       ├─ storage：S3 SDK 调用、上传、对象属性与校验
       ├─ backup：任务编排、状态转换、manifest 与重试
       └─ output：稳定 JSON、受控 stderr、错误分类
```

**实施约束**：

- 当前 `internal/app` 不需要在 M0 当场搬迁；优先定义接缝，再分批抽取。
- 每层的入口接受 `context.Context`；截止时间和取消传递到每一次外部调用，子进程不经过 shell。
- 将外部副作用放在清晰的接口后（例如 `EtcdRunner`、`ObjectStore`），仅在测试或职责隔离确有收益时引入接口；不创建空泛的插件框架。
- CLI 不负责 S3 重试、Manifest 更新或文件落盘策略；编排层不解析 CLI flag。
- 日志、错误、清单写入与输出应各有统一入口；单个失败不得在多个层重复打印敏感底层错误。
- 一次 PR 聚焦一个模块或行为，并运行原有测试，确保向后兼容。

## 4. 兼容性契约（M1-M3 实施时强制）

### 4.1 CLI 与退出码

保持当前命令、flag、默认配置兼容性（main 使用 `./config/config.yaml`，不存在时回退原 `./opskit.yaml`，不合并；显式 `--config` 不回退）、命令行参数优先于 YAML、以及位置参数约束；除非另有明确版本化迁移计划，不能直接修改脚本可见行为。

当前源码使用的退出码：`0` 成功、`1` 操作/检查失败、`2` 参数或配置错误、`3` 缺少依赖、`4` 总超时或取消、`5` 本地备份完成但上传/远端阶段失败。`130` 是旧设计文档中的中断目标，**目前不得称为已实现**；若将来实现，须测试 SIGINT/SIGTERM 和 Windows 行为。

stdout 的 JSON 在成功及检查失败场景保持可解析；诊断信息进 stderr。已使用的字段、类型与语义不得静默变更；新字段优先可选、向后兼容。错误输出是否统一为 JSON 是后续单独决策，不能凭设计文档就更改现有消费者约定。

### 4.2 YAML 配置

`schema_version: 1` 为当前有效配置。继续支持已有 `etcd`、`s3`、厂家选择及文档化的平铺旧字段；未知字段、重复 key、额外文档及无效超时应拒绝。继续保持“CLI > YAML > 内置默认值”。

新增配置能力优先采用明确的可选字段；如果必须引入不兼容结构，则提交单独的 `schema_version: 2` 迁移 RFC、兼容期限、迁移示例和回滚说明，**不默默迁移或重写用户配置**。`config init` 不覆盖现有文件。相对路径按配置文件位置解析；CLI 相对路径按工作目录解析。

对凭据来源进行显式验证：不完整的静态 S3 密钥对报配置错误；未选中厂家块不可泄露其凭据。优先鼓励环境变量、工作负载身份和 SDK 凭据链，但旧版静态凭据字段在兼容窗口内不直接删除。未来的 `*_env` 或 `*_file` 等设计必须先定义冲突优先级、空值语义和跨平台行为。

## 5. etcd 备份状态机

### 5.1 目标状态（**未实现的设计**）

```text
PENDING → VALIDATING → SNAPSHOTTING → LOCAL_VERIFIED
                                          │
                           ┌──────────────┴──────────────┐
                           │                             │
                      无远端上传                     UPLOADING
                           │                             │
                     COMPLETED_LOCAL             REMOTE_METADATA_VERIFIED
                                                         │
                                                 MANIFEST_PUBLISHED
                                                         │
                                                 COMPLETED_REMOTE

任一执行状态 → FAILED / CANCELLED
```

说明：

- `LOCAL_VERIFIED` 仅表示本地普通文件已完整写入、关闭并计算内容 SHA-256；不等于可恢复。
- `REMOTE_METADATA_VERIFIED` 仅表示对象 HEAD 返回的大小及 SHA-256 **metadata** 符合预期；元数据可能由上传者写入，不能等同于服务器实际字节回读。
- `COMPLETED_LOCAL` 明确无上传需求；`COMPLETED_REMOTE` 表示已按当前配置完成远端元数据验证并发布远端 manifest，不代表恢复演练完成。
- 未来另记录 `verification_level`：`local_sha256` / `remote_metadata` / `remote_checksum` / `remote_readback_sha256` / `isolated_restore`；该维度与任务执行 phase **正交**，不可单纯把“验证级别”当作阶段推进。
- `FAILED`、`CANCELLED` 需要同时记录 `failed_stage`，不可覆盖以前已经验证成功的本地产物信息。

### 5.2 持久化与重试原则

1. 目录和快照为独立任务空间；新建敏感文件建议权限 `0600`、新建任务目录 `0700`，并验证预先存在的父目录/符号链接及所有权风险；跨平台按可执行的系统权限模型适配。
2. 快照写入 `.partial`，检验非空、普通文件、内容 SHA-256 后再发布最终文件；目录、写入和 rename 失败均不报告成功。
3. Manifest 使用同目录临时文件、关闭后替换；实现前需要明确崩溃一致性、Windows 替换差异及适当的 `fsync` 策略。没有有效 manifest 的任务不能被判为可自动清理的已完成备份。
4. 上传前校验本地源文件仍与记录的 hash/size 一致，避免读文件期间变化。实际调用上传 SDK 需保留取消语义，审计 multipart 中断清理行为。
5. 上传失败时保留本地快照，标出 `failed_stage=upload`，仍使用退出码 `5`；**不能无限重试不可重试的授权/前置条件错误**。
6. 如果上传请求成功但后续 HEAD 或 manifest 失败，远端对象可能已存在。重试前必须先查询状态并决定继续校验或改用新 key，不能假定可以安全覆盖，也不能因为已有对象就假报完整成功。
7. 保留策略未实现。在未来实现前必须先有只读预览、严格目录归属检查、符号链接逃逸保护，以及上传成功前禁止删除唯一可用副本的限制。

### 5.3 Manifest 兼容设计

当前 manifest 是 v1，字段仅为 `schema_version`、`file`、`size`、`sha256`、`created_at`、`upload_status` 和可选 `remote_key`，实际实现见 `internal/app/app.go`。

**候选新增字段**（未来实现前应有测试和样本）：

| 字段 | 类型 | 语义 |
|---|---|---|
| `task_id` | string | 独立任务标识，不能凭路径猜测 |
| `phase` | string | 当前任务状态，采用已定义枚举 |
| `started_at` / `finished_at` | RFC3339 时间或空值 | 任务时间边界 |
| `verification_level` | string | 当前可证明的最高校验级别 |
| `failed_stage` / `error_code` | string，可选 | 无秘密的异常定位 |
| `artifact` | 结构体，可选 | 产物类型、路径/文件名、大小和 hash |
| `remote` | 结构体，可选 | 服务类型、桶、对象 key、验证结果 |

在更改 Manifest 之前必须决定是否追加可选 v1 字段或升级 v2；v1 原有字段不得悄然删除、改名或改变语义。新增解析器应有旧版 fixture 测试，验证中断时仍能读取既有清单。

## 6. S3/MinIO 存储契约

- `s3 check` 只读，不创建桶、不上传测试对象；HTTP 403 表示拒绝、404 可能是不存在或被隐藏，不能把这两者直接当作服务不可达。
- `HeadBucket` 成功不证明 `PutObject` 权限，`HeadObject` 成功不证明远端文件内容逐字节正确。
- 默认不覆盖已有对象。条件写支持需按后端实际测试，若服务不支持必须明确失败，不能退化为有竞争条件的 HEAD-后-PUT。
- 上传后先比较长度与 metadata SHA-256；未来可提供可选的服务端 checksum 或下载回读 SHA-256；发布远端 manifest 前必须满足当前约定的校验级别。
- S3 API 错误分类至少涵盖权限拒绝、对象已存在、目标未找到、连接问题、请求超时、SDK 身份不可用、checksum 不符；在诊断与 JSON 中不暴露 Authorization、签名 URL、Access Key、Session Token 或包含凭据的 endpoint。
- 兼容性报告必须标明经测试的 MinIO 版本、AWS S3 场景或其他兼容后端，不能泛称所有 S3 实现均支持相同条件写/multipart/checksum 语义。

## 7. 安全与错误输出契约

### 7.1 错误类别（设计目标）

| 类别 | 示例 | 退出码兼容策略 |
|---|---|---|
| `invalid_argument` / `invalid_config` | 缺参数、无效超时、厂家配置冲突 | `2` |
| `dependency_unavailable` | 未安装 `etcdctl` | `3` |
| `cancelled_or_timeout` | 总任务截止时间 / 主动取消 | `4`（先保持现状） |
| `operation_failed` | 查询失败、快照失败、校验失败 | `1` |
| `remote_stage_failed` | 本地快照成功但上传或远端校验失败 | `5` |

新内部错误码可以细分机器诊断（如 `CFG_INVALID`、`ETCD_SNAPSHOT_FAILED`、`S3_ACCESS_DENIED`），但原始整数退出码在兼容窗口内不得改变。不要把敏感原始 `stderr` 携带到错误字符串中；脱敏后只展示阶段、错误类别和可操作的排查建议。需权衡过度隐藏诊断信息与安全性，可在未来设计有白名单的非敏感结构化字段。

### 7.2 秘密与文件权限

- 敏感数据来源包括配置 `access_key/secret_key/session_token`、`ETCDCTL_USER`、证书私钥、签名 URL 和 SDK 原始认证错误。
- 任何日志、异常、测试结果、PR、构建附件和 manifest 都不保存秘密；新增测试使用伪凭据并检查原始子进程错误中的标记不会泄露。
- 不采用 `sh -c` 拼接用户输入；禁止关闭 TLS 证书验证作为默认“排错方案”。
- 强制限制凭据文件与备份临时文件权限，并测试 Windows/Linux/macOS 的实际安全边界；权限无法保证时不得虚报受保护。
- 不打印全部环境变量，不采集真实生产配置作为 CI fixture。

## 8. CI/CD 与验收矩阵

当前 `.github/workflows/ci.yml` 已实现：

- pull request / main push：Ubuntu、Windows、macOS 各自执行 `go vet ./...` 与 `go test -race ./...`。
- 测试成功后：交叉构建 linux/darwin/windows 的 amd64/arm64，上传构建附件与 SHA-256 列表。
- `v*` tag：执行发布工作流并尝试同步首页下载表。

下列为未来 PR 的增量验收，不把“设计上应有”写成“已运行”：

| 优先级 | 验证层 | 正例与负例 | 通过门槛 |
|---|---|---|---|
| P0 | Go 基础 | gofmt、`go test`、`go vet`、Race、六目标交叉构建 | 无格式差异、测试全部通过、构建成功 |
| P0 | 配置契约 | 旧 YAML、未知/重复字段、非法 timeout、CLI 优先级、厂家冲突 | 向后兼容；无秘密输出 |
| P0 | 备份故障注入 | 子进程失败/取消、空快照、磁盘写入失败、SHA-256、上传拒绝、HEAD 失败 | 退出码正确；不伪报成功；本地有效备份保留 |
| P0 | S3 端到端 | 隔离 MinIO 上传、目标已存在、metadata 校验、拒绝访问、取消 | 记录版本、对象状态及可复现结果 |
| P0 | etcd 隔离恢复 | 在临时 etcd 写入已知数据→快照→隔离目录恢复→查询核对数据 | 恢复成功，数据与预期匹配，未触碰生产 |
| P1 | 安全检查 | `govulncheck`、凭据泄露回归测试、最小权限 | 严重问题阻断发布，误报/例外可追踪 |
| P1 | 发布脚本 | `scripts/download_links.py` 的固定版本链接、非法输入、幂等性、标记保护 | 不错写首页、不生成错误版本链接 |
| P1 | 多环境兼容 | Linux/macOS/Windows 测试机与实际 etcd/MinIO 版本矩阵 | 报告成功与未覆盖范围，不推断全部兼容 |

验收原则：

1. **隔离环境**：集成测试用临时容器/临时目录/测试凭据；CI 禁止接入生产地址。
2. **可复现**：固定服务版本与命令，记录环境、测试数据、预期结果和失败日志脱敏策略。
3. **功能证据**：本地 `SHA-256` 和远端 metadata 对比不替代恢复演练。
4. **质量门禁**：PR 要通过与其变化相关的单测和回归；发布必须通过已规定的发布测试，不以“build success”代替完整验证。
5. **安全发布**：工作流最小权限；发布标签需明确授权；任何未完成验证的能力在 Release Notes 标注限制。

## 9. 里程碑与交付顺序

| 里程碑 | 交付范围 | 验收出口 |
|---|---|---|
| **M0 设计基线（本 PR）** | 明确实际能力、兼容契约、状态机、权限、安全、CI 和实施顺序 | 设计文件审查通过；无业务代码变更 |
| **M1 核心可靠性** | 备份状态、manifest 向后兼容设计落地、失败保留、权限/取消/重试 | 单元及故障注入测试；旧配置与脚本不回归 |
| **M2 真实验证** | 临时 etcd + MinIO 集成测试、隔离恢复演练、内容校验能力 | 留存版本矩阵与可复现报告，不触达生产 |
| **M3 架构和体验** | 按需抽离 config/etcd/storage/backup/output，统一安全诊断 | 现有 CLI/JSON/退出码契约不变，回归测试通过 |
| **M4 按需扩展** | S3 下载/列举、保留策略、网络诊断、MySQL/PG 等 | 每个功能独立 RFC、验收矩阵与文档，不一次性铺开 |

每个里程碑拆为小 PR；**M0 合并不授权自动实施 M1 及以后，也不授权自动合并或发布**。评审时优先回答：用户是否能验证备份结果？发生部分失败时会不会丢数据？旧自动化脚本会不会坏？生产凭据是否可能泄露？

## 10. 风险与待实施前核对项

| 风险 | 对策 | 阶段 |
|---|---|---|
| Manifest 新字段与现有脚本冲突 | 固定 v1 fixtures，先讨论版本策略 | M1 |
| 快照完成但远端 HEAD / manifest 失败 | 保留本地，远端对象独立排查，不直接覆盖同 key | M1 |
| 已存在备份根目录权限过宽或符号链接逃逸 | 在创建/清理策略里检查，避免自动删除 | M1 |
| 子进程原始 stderr 泄露敏感信息 | 用安全错误分类替代原始打印，保留有限诊断 | M1 |
| MinIO 后端对条件写、多段上传支持差异 | 实际集成测试并记录版本，不依赖推测 | M2 |
| 恢复实验影响在线 etcd | 仅允许隔离目录、临时实例和示例数据 | M2 |
| 将远端 HEAD 误当作恢复证明 | 区分验证级别与任务状态，公开限制 | M1/M2 |
| CI 持续时间和成本增大 | 快速门禁与较重隔离集成测试分层；发布前必须完成规定项目 | M2 |
